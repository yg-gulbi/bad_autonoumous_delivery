# 강의실에서 실제 로봇 두 대 연결하기

침상형 이송 로봇(Robot A)은 `/robot3`, 약품 운송 로봇(Robot B)은 `/robot2`다 (11/19 확정, D-29). 관제 PC에서 발견 서버를 계속 켜 두고, 같은 PC의 두 번째 터미널에서 연결을 점검한 뒤 관제와 화면을 실행한다. 현장 시험은 이 문서의 실제용 launch로 진행한다. 시연용 mock도 실물과 같은 로봇 이름을 사용하므로 먼저 시연 프로세스를 종료한다.

## 1. 팀원과 현장 준비

- **PART 04** 담당자는 로봇별 Nav2와 `hospital_nav` 명령 노드를 켠다. 두 로봇과 주행 노트북이 관제 PC의 발견 서버를 바라보며 같은 `ROS_DOMAIN_ID`와 `RMW_IMPLEMENTATION`을 쓰는지 확인한다. 두 로봇 모두 `main_map/main_maps.yaml`에서 실제 위치와 방향을 초기화한다.
- **로봇 옆 담당자**는 도크 앞 공간과 실제 지도 위치를 확인한다. 도크에서 첫 MOVE를 시작하면 자동 언독 뒤 위치 준비를 거친다. 로봇이 떨어져 출발하는 모습과 정지를 현장에서 확인한다.
- PART 04의 `keyboard_control` 창에서 **Q**로 종료한다. 같은 로봇에 명령을 보낼 수 있는 다른 시험 노드도 종료한다.
- **PART 05** 담당자는 침상 감시를 실행한다. 침상 감시 없이 시험할 때는 현장 운영자가 결정 카드에서 **감시 없이 운행**을 선택한다.
- **PART 06** 담당자는 상자 시연 때 1번 프로그램을 로봇마다 켠다 (아래). 분류기가 없으면 Nav2가 포기했을 때 "장애물 판별 불가" 카드에 로봇이 찍은 사진만 나온다.

### 로봇 PC 대응

| 로봇 PC | 역할 | 관제 이름 | 홈 | 도크 |
|---|---|---|---|---|
| robot3 PC | 침상형 이송 로봇 | `robot_a` (A) | D | 미등록 |
| robot2 PC | 약품 운송 로봇 | `robot_b` (B) | F | 조제실(F) 쪽 (-0.330, -5.110, -3°) |

**로봇 PC는 hospital_nav를 다시 빌드한다.** 4J 관제는 main `5b7418f`의 자리 2개(`MOVE F2`), 교차로 경유(`VIA_PASSED`), 장애물 사진(`OBSTACLE`)을 쓴다. 예전 빌드도 움직이지만 2번 자리를 쓰지 않고 장애물 사진이 오지 않는다 (preflight가 경고한다).

```bash
cd ~/<로봇 워크스페이스> && git pull && colcon build --packages-select hospital_nav && source install/setup.bash
```

### 각 로봇 PC에서 hospital_nav 실행

각 PC에서 ROS Jazzy, 팀 워크스페이스와 발견 서버 환경을 불러오고 해당 로봇의 Nav2를 준비한다. 설치할 ROS 패키지 이름은 `hospital_nav`다. robot3 PC(침상형)에서 실행한다.

```bash
ros2 run hospital_nav command_receiver --robot robot3
```

robot2 PC(약품 운송)에서 실행한다.

```bash
ros2 run hospital_nav command_receiver --robot robot2
```

### PART 06 장애물 분류기 (상자 시연)

PART 06 담당자가 발견 서버 환경에서 로봇마다 하나씩 켠다. 상자 시연은 약품 운송 로봇(robot2)으로 한다.

```bash
ros2 run part6_obstacle_classifier obstacle_classifier --ros-args -r __ns:=/robot2
ros2 run part6_obstacle_classifier obstacle_classifier --ros-args -r __ns:=/robot3   # 침상형도 볼 때
```

## 2. 관제 PC 터미널 준비

새 터미널을 열 때마다 팀 가상환경과 설치된 워크스페이스를 불러온다. 가상환경 위치가 다르면 첫 줄만 해당 PC의 경로로 바꾼다.

```bash
source ~/venvs/rokey_venv/bin/activate
source /opt/ros/jazzy/setup.bash
cd ~/bad_ws
source install/setup.bash
```

새 관제 버전을 설치할 PC에서는 `~/bad_ws`에서 아래 명령을 한 번 실행하고, 다른 터미널에서도 새 설치를 불러온다.

```bash
colcon build --packages-select part3_fleet_manager part1_ui_dashboard
source install/setup.bash
```

**터미널 1 · 발견 서버.** `hostname -I`로 로봇과 같은 네트워크에 연결된 인터페이스의 주소를 확인한다. 아래는 2026-11-18 강의실에서 사용한 주소다. 주소가 달라졌으면 서버와 모든 클라이언트의 주소를 함께 바꾼다.

```bash
/usr/bin/fastdds discovery --server-id 0 --ip-address 192.168.108.31 --port 11811
```

**터미널 2 · 점검, 관제, 화면.** 가상환경과 워크스페이스를 불러온 새 셸에서 아래를 실행한다. 추가로 여는 관측 터미널도 같은 환경을 사용한다. 격리 시험의 `LOCALHOST`, 시험 도메인 번호 또는 루프백 전용 DDS 프로필을 가져오지 않는다.

```bash
export ROS_DISCOVERY_SERVER=192.168.108.31:11811 ROS_SUPER_CLIENT=True
printenv ROS_DOMAIN_ID RMW_IMPLEMENTATION
ros2 run part3_fleet_manager preflight
```

`ROS_DOMAIN_ID`와 `RMW_IMPLEMENTATION`은 PART 04와 확인한 값을 쓴다. preflight 첫 다섯 줄에서 셸 환경을 확인한다. 화면·관제·점검 도구는 이 값을 설정하지 않는다.

## 3. 점검 결과 읽기

| 확인할 줄 | 현장에서 볼 값과 조치 |
|---|---|
| 발견 서버 | 지정한 로컬 UDP 포트의 소유자가 Fast DDS여야 한다. 포트 없음은 터미널 1, 주소 불일치는 관제 PC의 IP, 소유자 확인 불가는 서버 실행 계정과 소켓 조회 권한을 확인한다. |
| Robot A, Robot B | 10초간 동시에 관측한다. 필수 네 줄은 최신 hospital_nav STATE와 그 안의 battery·pose·docked다. 각각 OK인지, 위치·잔량·도킹 값이 실물과 맞는지 확인한다. 도크 위와 도크 밖은 모두 유효한 값이다. 원본 battery_state·dock_status·amcl_pose와 Nav2 액션은 참고다. hazard_detection은 기본 ‘사용 안 함’이다. |
| 명령 발행자 | 관제 시작 전에는 없음이 정상이다. 이미 `/fleet_manager`가 있으면 두 번째 관제를 띄우지 않는다. 다른 발행자가 표시되면 이름을 확인하고 해당 노드를 끈 뒤 다시 점검한다. |
| 자리 번호 | 로봇마다 `자리 번호(STATE.slot) · 있음 (2번 자리 사용)`이 정상이다. ‘예전 PART 04 — 2번 자리 사용 안 함’이면 그 로봇 PC의 hospital_nav를 다시 빌드한다. 실행은 막지 않는다. |
| 침상 감시·장애물 분류 | `/patient/bed_exit`의 수신 Hz와 마지막 값을 본다. 0 Hz면 PART 05의 실행 여부를 확인한다. 로봇마다 `/<ns>/hospital_nav/obstacle_image · 구독자 1 (/robot2/obstacle_classifier)`처럼 PART 06이 보여야 상자를 판별한다. ‘장애물 분류기 없음 — 상자 판별 없이 사진만 표시’는 경고이고 실행은 막지 않는다. |
| 구역 대조 | `자리 2개·교차로 (SLOTS) · OK`가 정상이다. A~F의 1번·2번 자리와 교차로 좌표 차이가 0.05 m를 넘으면 관제 좌표와 PART 04 좌표가 함께 표시된다. 빠진 구역도 표시된다. ‘예전 형식 (GOALS, 자리 1개)’이면 관제 PC의 PART 04 소스가 5b7418f 이전이다. 사용 맵과 주행팀의 목표 좌표를 대조한다. 소스가 다른 위치에 있으면 `--goals-file /절대경로/goal_manager.py`, 다른 관제 설정을 쓸 때는 `--config-file /절대경로/fleet.yaml`을 지정한다. |

마지막 판정 **실제 실행 가능**은 필수 인터페이스가 연결됐다는 뜻이다. **실제 실행 안 됨**이면 이유가 한 줄씩 나온다. 해당 항목을 복구한 뒤 점검을 반복한다. 점검은 명령 발행, 주행 목표 전송, 서비스 호출, 카메라 촬영 요청을 하지 않는다.

## 4. 관제와 화면 켜기

터미널 2의 환경을 그대로 사용한다. 설치된 `fleet.yaml`과 기본 실제 DB `~/.bad/bad_real.db`를 쓰는 명령이다.

```bash
ros2 launch part1_ui_dashboard real.launch.py
```

관제 설정 또는 지도의 위치를 명시하려면 같은 launch에 인자를 준다. `bed_monitor_require_at_start`를 생략하면 해당 `fleet.yaml`의 정책이 적용된다.

```bash
ros2 launch part1_ui_dashboard real.launch.py \
  config_file:="$(ros2 pkg prefix --share part3_fleet_manager)/config/fleet.yaml" \
  map_yaml:="$PWD/main_map/main_maps.yaml" db_path:="$HOME/.bad/bad_real.db"
```

[관제 화면](http://localhost:8090/)에서 연결 **2 / 2**, 두 로봇의 위치, 침상 감시 배지를 확인한다. 현장에서 사용할 조작자 이름을 입력한다.

## 5. 주행 시험 순서

| 순서 | 화면 조작 | 현장에서 확인할 결과 |
|---|---|---|
| 1. 한 대 짧은 이동 | 종합 관제 지도에서 가까운 구역을 누르고 대기 중인 로봇 한 대를 고른다. | 도크 위라면 ‘도크에서 출발 준비’가 보이고 언독·위치 초기화 뒤 주행한다. 출발 준비 중 막힘 카드는 열리지 않는다. 준비가 120초를 넘으면 NAV_FAILED 카드를 확인한다. 지정한 로봇의 실제 도착 위치와 지도를 대조한다. |
| 2. 정지·재개 | 짧은 이동 중 **안전 정지 요청**을 누른다. 로봇 옆 담당자가 정지를 확인하고 경로가 비었을 때 **전체 재개**를 누른다. | 실제 바퀴가 멈췄다가 허용 후 다시 움직인다. 운영 기록에 조작자 이름이 남는다. |
| 3. 호출 한 건 | **이송 작업 → 이송 요청 → 호출**에서 목적지를 등록한다. 도착 후 확인 항목을 체크하고 **수령 완료**를 누른다. | 호출이 완료 탭에 남고 담당 로봇이 홈으로 복귀한다. |
| 4. 두 대 동시 임무 (시나리오 1) | 환자 이송 C→A와 물품 F→E→B를 접수한다. 두 대가 이동 중일 때 후속 환자 이송 D→A와 물품 F행을 등록한다. 각 도착을 확인한다. | 두 대가 동시에 임무를 맡고 후속 요청은 대기한다. 기본 ROLE에서는 환자는 A, 약품·호출은 B가 맡는다. 완료 탭에서 네 건을 확인한다. |
| 5. 방향별 복도 통행 (시나리오 2) | 기본 `DIRECTIONAL`에서 Robot A를 E방, Robot B를 위쪽 홀에 둔다. B를 C로 보낸 뒤 복도 진입을 확인하고 A를 D로 보낸다. | B 통행 중 A는 E방 안에서 진입 전 대기한다. 복도 보유자는 B다 (4J부터 방 안에서 기다리는 로봇은 문 허가를 쥐지 않는다). B가 완전히 나간 뒤 A가 출발한다. A는 교차로에 섰다가 위로 간다. 복도 양보 정지·접촉이 없어야 한다. |
| 6. 2번 자리 | 약품 운송 로봇이 F(홈)에 쉬는 동안 침상형 이송 로봇을 F로 보낸다. | 명령 토픽에 `MOVE F2 1`, 목적지 대기 없이 조제실(F) 2번 자리(입구 쪽)에 선다. 로봇 블록과 운영 기록에 "조제실(F) 2번 자리". |
| 7. 교차로 | B방 1번 자리에 한 대를 두고 다른 로봇을 B로 보낸다. 이어서 같은 홀의 두 로봇을 B와 E로 동시에 보낸다. | 두 번째 로봇은 교차로에서 방향을 맞춘 뒤 102호 병실(B) 2번 자리로 들어간다. 동시 출발에서는 뒤 로봇이 ‘교차로에 … 있음 → … 대기’로 교차로 밖에서 기다리다가 앞 로봇이 교차로를 벗어나면 출발한다. |
| 8. 상자 (PART 06 켬) | 약품 운송 로봇이 복도를 지날 때 그 앞에 의료용 상자를 놓는다. | 약 5초 뒤 Nav2 포기 → 상자 카드(사진과 ‘판별: 의료용 상자 0.93’, ‘의료용 상자가 길을 막고 있음 (로봇 앞 약 0.4 m)’) → 복도 막힘, 다른 로봇 복도 진입 보류. 상자를 치우고 [치웠음, 다시 출발] → 해제·재출발. 상자가 안 보이면(‘의료용 상자는 보이지 않음’) 저절로 다시 가지 않고 카드가 뜬다 (4K, `retry_if_clear: false`). |

- **시연에서는 4막(상자)을 건너뛴다** (D-31). 시연 5막 순서는 BRIEF 9장 61번(`test_4j_demo.py`)이고, 시험과 BRIEF 61번은 그대로 둔다. 위 8번은 상자를 따로 확인할 때만 한다.

현장에서 복도를 한 대씩 사용하려면 두 로봇이 임무를 마치고 복도 밖에 정지했는지 확인한다. 현재 관제·화면 launch를 Ctrl+C로 종료한 다음 같은 셸에서 아래처럼 다시 실행한다. 별도 DB나 지도를 지정했다면 기존 인자도 다시 준다.

```bash
ros2 launch part1_ui_dashboard real.launch.py corridor_mode:=EXCLUSIVE
```

기본 운행의 충돌 방지는 위치로 확인한다. 반대 방향 복도 진입 보류, 선행 로봇과의 간격, 목적지에 다른 로봇이 있을 때 출발 보류, 근접 정지를 순서대로 확인한다. 기본 `safety.use_hazard_topic: false`에서는 범퍼 수신 시험을 생략한다.

두 로봇의 기본 복귀는 홈 구역이다. 도크 복귀를 시험할 때는 PART 04의 도크 위치·방향과 도크 앞 0.6 m 접근 경로를 실제 배치와 대조하고, 시험용 fleet.yaml의 해당 로봇에만 `return_to: DOCK`을 설정한다. robot2 도크는 조제실(F) 쪽에 있다. 먼저 F를 비우고 임무를 완료한 뒤 DOCKING, DOCKED 또는 같은 임무의 COMPLETE와 docked=true, 충전 표시를 확인한다. robot3는 PART 04 도크 좌표가 등록될 때까지 ZONE으로 운용한다.

침상 이탈 또는 감시 끊김이면 정지 사유를 먼저 확인한다. 신호가 돌아와도 저절로 재개하지 않는다. 현장이 안전한지 확인하고 운영자가 재개한다.

## 6. 비상시와 종료

- 비상시 화면 위쪽 **안전 정지 요청**을 누르고 로봇 옆 담당자에게 즉시 알린다. 로봇이 멈췄는지 현장에서 확인한다. 통신이 끊겼거나 정지가 확인되지 않으면 옆 담당자가 로봇 자체의 정지 조작을 한다.
- 시험이 끝나면 두 로봇이 정지한 것을 확인하고 터미널 2의 launch를 Ctrl+C로 종료한다. SQLite 연결이 닫힌 뒤 `~/.bad/bad_real.db`를 보관한다. 사용자 지정 DB를 썼으면 해당 경로에서 수집한다.
- 관제·로봇 화면 캡처, 작업 번호와 시각, 운영 기록, 해당 실행의 ROS 로그(기본 `~/.ros/log/`, `ROS_LOG_DIR` 지정 시 그 경로)를 함께 보관한다. 팀원들의 시험이 끝나면 터미널 1의 발견 서버를 종료한다.

설치와 개별 노드로 연결했던 명령은 [관제 PC 설치 기록](CONTROL_PC_SETUP.md), mock에서 사용한 요청과 관측값은 [시나리오 기록](stage3-scenarios.md)에 있다.

## 4N 출구와 접근 간격 확인

1. preflight와 관제 시작 로그의 간호 스테이션(D) 출구 경고를 확인한다. 현장에서 1번 자리에서 입구까지의 주행선과 2번 자리 간격을 확인한 뒤 설정값을 결정한다.
2. 수술실(C) 1번 자리에 한 대를 세우고 반대편에서 다른 로봇을 수술실(C) 2번 자리로 보낸다. 도착 반경 안에서는 1번의 출발이 보류되고, 도착 뒤에도 2번 자리가 막고 있으면 기다리는지 확인한다. 2번 로봇이 떠나 충분히 멀어진 뒤 1번 로봇이 출발한다.
3. 반대로 출구를 먼저 사용하는 로봇이 있으면 도착 차량이 2.0 m 반경 밖에서 멈추는지 확인한다. 실제 위치 수신 간격, 정지 거리와 해제 거리를 함께 기록한다.
